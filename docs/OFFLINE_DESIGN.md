# 오프라인 설계

GoldenTimeAED가 인터넷 없이 동작하는 방식과, 왜 이런 구조가 될 수밖에 없었는지를 기록한다.

## 왜 오프라인이어야 하나

AED는 평상시엔 쓸 일이 없다가 심정지 상황에 딱 한 번 쓰는 앱이다. 그런데 지하 주차장,
엘리베이터, 지하철역, 대형 건물 내부처럼 **네트워크가 약한 곳일수록 대응이 필요한 장소**다.
"인터넷이 되면 동작하는 앱"은 정작 필요한 순간에 안 켜질 수 있다.

---

## 제약: 웹에서는 오프라인 "지도"가 불가능하다

이 설계의 출발점이자 가장 오해하기 쉬운 부분이다.

**네이버 지도 JS API v3는 오프라인에서 타일을 렌더링할 수 없다.** 타일(지도 이미지 조각)을
매 요청마다 서버에서 받아오는 구조이고, 약관상 타일을 저장해두는 것도 제한된다.

**지도 회사를 바꿔도 해결되지 않는다.** 구글·카카오도 웹 API는 전부 온라인 전용이다.
흔한 오해가 하나 있는데, 구글 지도 **앱**에는 오프라인 지도 기능이 있지만
**Google Maps JavaScript API**(웹페이지에 지도를 넣는 것)에는 없다. 그리고 앱이 받아둔
오프라인 지도는 그 앱 안에만 있어서 웹페이지가 꺼내 쓸 수 없다.

> 웹에서 오프라인 지도를 하려면 타일을 직접 호스팅하는 방법(MapLibre GL JS + PMTiles)뿐인데,
> 한국 전역 타일이 수백 MB라 Cloudflare Pages의 파일당 25MB 제한을 넘고 R2 같은 별도
> 스토리지가 필요하다. 지도 스택 전면 교체를 수반해 이 프로젝트 범위 밖으로 두었다.
> 경로 안내(길찾기)도 마찬가지로 온라인 전용이며, 오프라인 라우팅은 도로망 데이터가 별도로 필요하다.

### 그래서 내린 결정

| 상태 | 화면 |
|---|---|
| 온라인 | 네이버 지도 + 마커 (`map-view.js`) — 기존과 동일 |
| 오프라인 | Canvas 간이 지도 + 나침반 + 거리순 목록 (`offline-view.js`) |

오프라인 화면은 지도 타일 없이 Canvas에 직접 그린다. 내 위치를 중심에 두고 주변 AED를
점으로 찍고, 거리 동심원(100/300/500m)과 방위 눈금을 그리고, 기기 방향에 따라 회전시킨다.
도로는 안 보이지만 **"어느 방향으로 몇 m"** 는 정확히 전달된다. GPS는 네트워크 없이도
동작하므로 "내 위치 기준 가장 가까운 AED"라는 핵심 가치는 오프라인에서도 지켜진다.

가장 가까운 3개는 캔버스에 **숫자(1·2·3)** 로 표시하고 이름은 아래 목록에서 확인한다.
도심에서는 가까운 AED들이 한곳에 몰려 있어 캔버스에 이름표를 붙이면 서로 겹쳐
아무것도 읽을 수 없기 때문이다.

> **오프라인 뷰는 온라인에서도 '목록' 버튼으로 볼 수 있다.** 오프라인 전용 코드는 평소에
> 실행되지 않아 검증되지 않은 채 남고, 정작 필요할 때 깨진다. 항상 쓰이게 만들어 이를 막는다.

## 데이터 흐름: 다운로드는 **두 번** 일어난다

"GitHub Actions가 매일 밤 받는 것"과 "사용자 기기에 받는 것"은 서로 다른 다운로드다.
이 구분이 이 문서에서 가장 중요하다.

```
[1단계] 매일 01:17 KST — 서버 쪽 (사용자와 무관하게 알아서 돌아감)
──────────────────────────────────────────────────────────────
  GitHub Actions (.github/workflows/sync-aed.yml)
    → safetydata.go.kr API 전량 호출      (backend/sync.py)
    → 변환·중복제거·안정정렬 후
       frontend/data/aed-snapshot.json 생성
    → 행 내용이 바뀐 날에만 커밋 & push
         └→ push가 Cloudflare Pages 재빌드를 자동으로 유발

  결과: 인터넷에 "항상 최신인 파일" 한 개가 놓여 있음


[2단계] 사용자가 "온라인"으로 앱을 열 때 (1단계와 무관, 아무 때나)
──────────────────────────────────────────────────────────────
  브라우저 (frontend/sync-data.js)
    → data/aed-meta.json 먼저 확인 (수백 바이트)
    → 저장본과 generated_at이 다르면
       data/aed-snapshot.json 다운로드 (압축 전송 2~3MB)
    → IndexedDB에 저장               (frontend/data-store.js)

  결과: 사용자 기기 안에 데이터 사본이 생김


[3단계] 사용자가 "오프라인"일 때
──────────────────────────────────────────────────────────────
  브라우저
    → 네트워크를 아예 쓰지 않음
    → IndexedDB에서 읽음
    → Canvas 간이 지도 + 거리순 목록 표시

  결과: 인터넷 없이 동작
```

### 여기서 따라 나오는 것들

- **오프라인일 때는 다운로드가 불가능하다.** 오프라인이니까. 그래서 오프라인이 되기 전에
  미리 받아두는 것(프리페치)이 오프라인 지원의 전부다.
- **2단계가 한 번도 일어나지 않았으면 3단계는 빈 화면이다.** 그래서 사용자 조작 없이
  **첫 방문 시 백그라운드로 자동으로 받는다.** 버튼에 의존하면 안 누른 사람은 정작
  응급 상황에 아무것도 못 본다.
- **사용자가 2주 동안 앱을 안 열었다면** 기기에는 2주 전 데이터가 있다. AED 위치는 자주
  바뀌지 않으므로 실용상 문제가 없고, 화면 상단 배너에 "마지막 갱신 8월 18일"을 표시한다.
- **스냅샷은 저장소에 커밋한다.** Pages는 커밋 푸시 때만 빌드하므로, 데이터가 저장소 안에
  있으면 **push가 곧 배포**가 되어 Deploy Hook이라는 배선이 통째로 사라진다. 버전 관리되어
  롤백과 diff 확인도 쉽다.
- **매일 10MB가 쌓이지 않는 이유**: `sync.py`가 새로 만든 행 배열을 커밋된 것과 비교해
  **다를 때만** 파일을 쓴다. 같은 날은 파일이 바이트 단위로 그대로라 커밋도, 재빌드도 없다.
  그래서 `generated_at`의 의미도 "동기화를 돌린 시각"이 아니라 **"데이터가 마지막으로 바뀐 시각"**이다.
- **이게 성립하려면 정렬과 id가 결정적이어야 한다.** 좌표 기반 자연키로 정렬하고 그 sha1에서
  id를 만드는 이유가 이것이다. 순번을 id로 쓰면 행 하나만 추가돼도 이후 전체가 밀려
  파일 전체가 바뀌고, git이 delta를 잡지 못한다. **이 규칙을 깨지 말 것.**

## 스냅샷 포맷

`frontend/data/aed-snapshot.json` — 키 이름을 매 행마다 반복하지 않는 배열 포맷.
그냥 객체 배열로 두는 것보다 약 40% 작다. 좌표는 소수점 5자리(약 1.1m 정확도)로 반올림한다.

```json
{
  "generated_at": "2026-08-18T01:30:00+00:00",
  "count": 62431,
  "fields": ["id","org_name","install_place","address_road","lat","lng","phone"],
  "rows": [[1,"서울시청","본관 1층 로비","서울 중구 세종대로 110",37.56663,126.97795,"02-***-1234"]]
}
```

`frontend/data/aed-meta.json` — `generated_at`과 `count`만 담은 수백 바이트 파일.
앱은 이것만 먼저 받아 비교하므로, 데이터가 그대로면 2~3MB를 다시 받지 않는다.

`fields` 순서는 하드코딩하지 않고 `sync-data.js`가 파일이 선언한 순서를 읽는다.
나중에 컬럼이 추가·재배치되어도 값이 조용히 어긋나지 않게 하기 위해서다.

**크기**: 전국 약 62,000건 기준 raw ~9MB, Cloudflare가 brotli로 압축해 실제 전송은 2~3MB.
Pages의 파일당 25MB 제한 이내이고 IndexedDB에도 여유 있게 들어간다.
느려지면 `sido_name` 기준 시도별 분할을 검토한다(현재는 단일 파일).

## 저장소 역할 분담

| 저장소 | 담는 것 | 관리 주체 |
|---|---|---|
| Cache Storage | HTML/CSS/JS/아이콘 — **앱이 실행되기 위한 것** | `frontend/sw.js` |
| IndexedDB | AED 데이터 — **앱이 보여줄 것** | `frontend/data-store.js` |
| localStorage | 마지막 GPS 위치, 설치 안내 노출 여부 | `frontend/app.js` |

서비스워커는 **스냅샷(`/data/*`)을 일부러 가로채지 않는다.** IndexedDB가 이미 갖고 있어
여기서도 캐시하면 2~3MB를 이중 저장하게 되고, 갱신 시점을 앱이 통제하기 어려워진다.
네이버 지도(`oapi.map.naver.com`)도 가로채지 않는다 — 약관 문제이고, 어차피 오프라인에서는
지도 대신 오프라인 뷰가 뜬다.

## 설치(PWA)는 왜 권하나

**설치는 오프라인 동작의 필수 조건이 아니다.** 서비스워커는 일반 브라우저 탭에서도 동작하므로,
한 번 온라인으로 방문한 뒤에는 북마크를 비행기 모드에서 열어도 앱이 뜬다.

설치를 권하는 이유는 편의가 아니라 **저장소 보존**이다.

| | 설치 안 함 (브라우저 탭) | 홈 화면에 설치 |
|---|---|---|
| 오프라인 동작 | 됨 | 됨 |
| **iOS Safari 저장소 유지** | **7일 미방문 시 삭제됨** | 삭제 안 됨 |
| 응급 시 실행 | 브라우저 열고 북마크 찾기 | 아이콘 한 번 탭 |

iOS Safari는 ITP 정책상 7일 동안 방문하지 않은 사이트의 서비스워커/IndexedDB를 지운다.
홈 화면에 추가된 웹앱은 이 규칙에서 제외된다. **AED 앱은 "7일 이상 미사용"이 기본 상태**라
설치하지 않으면 정작 필요한 순간에 캐시가 비어 있을 가능성이 높다.

그래서 설치를 강제하지 않되, 스냅샷 저장이 끝나면 안내를 1회 노출하고
`navigator.storage.persist()`로 영구 저장소를 요청한다(`data-store.js`).

## 실패해도 앱을 막지 않는다

이 재설계 전에는 오프라인에서 앱이 가장 나쁜 방식으로 깨졌다.

1. `index.html`이 supabase-js를 jsDelivr CDN에서 로드 → 오프라인이면 `window.supabase`가
   undefined → `app.js`에서 TypeError → **에러 화면조차 못 띄우고 백지 화면**
2. 그걸 넘겨도 네이버 지도 스크립트 로드 실패 → `fatal()`이 전체 화면 오버레이로 앱을 잠금

지금은 모든 실패가 오프라인 뷰로 흡수된다. 전체 화면 오버레이(`fatal`)는 제거했다.

| 실패 | 동작 |
|---|---|
| 네이버 스크립트 로드 실패 (오프라인) | 오프라인 뷰 |
| 네이버 키 무효 / 도메인 미등록 | 오프라인 뷰 + 원인 안내 |
| 네이버 SDK가 깨진 채 로드됨 | 오프라인 뷰 + 안내 (`app.js`가 `naver.maps.Map` 존재를 확인하고 `init`을 try/catch) |
| `config.js` 없음 | 오프라인 뷰 + 안내 |
| 스냅샷 다운로드 실패 | 저장본으로 계속 동작 |
| 저장본도 없음 | "인터넷에 연결한 상태로 한 번 열어주세요" 안내 |

프론트엔드는 어떤 API도 직접 조회하지 않으므로 supabase-js CDN 의존성과 키 노출이 함께 사라졌다.
이후 Supabase 자체를 걷어내면서(→ API에서 받아 바로 스냅샷을 만들어 커밋) 남아 있던
빌드 시점 의존성도 없어졌다. 지금 프론트엔드가 읽는 것은 같은 도메인의 정적 파일뿐이다.

## 로컬에서 오프라인 확인하기

`file://`로 열면 서비스워커가 등록되지 않는다. 반드시 HTTP로 서빙할 것.

```bash
set -a && . ./.env && set +a
sh frontend/build-config.sh          # config.js 생성 (data/는 이미 커밋되어 있다)

cd frontend && python -m http.server 8000
```

1. `http://127.0.0.1:8000` 접속 → 데이터 저장 완료 메시지 확인
2. DevTools → Application → IndexedDB → `goldentime`에 데이터가 있는지 확인
3. DevTools → Network → **Offline** 체크 → 새로고침
4. 백지나 전체 화면 오류 없이 **간이 지도 + 목록**이 떠야 한다

나침반은 실기기에서만 검증된다. iOS는 `DeviceOrientationEvent.requestPermission()`이
사용자 제스처를 요구하므로 "나침반 켜기" 버튼을 눌러야 하고, 권한을 거부해도
북쪽 고정으로 정상 동작한다.
